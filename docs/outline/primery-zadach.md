# Примеры задач

## Пример 1. Общая среда запуска для нескольких команд

Проблема: каждая команда собирает свой способ запуска агентов, и правила организации легко обойти.

Действия инженера:

- Сделать повторно используемый запуск агентов.
- Подключить нужные инструменты и разделить данные и ресурсы команд.
- Подготовить документацию и примеры.

Ожидаемый результат: команды сами запускают сценарии через платформу с едиными правилами и не разрабатывают отдельную среду.

## Пример 2. Подключить новый инструмент

Проблема: агенту нужен внутренний трекер, но широкий доступ позволяет сделать лишнее.

Действия инженера:

- Описать формат запросов.
- Выдать только право создавать задачи, задать таймаут и лимит повторов.
- Включить запись вызовов.

Ожидаемый результат: инструмент есть в каталоге. Создание задачи работает, удаление отклоняется, оба события видны в журнале.

## Пример 3. Продолжить многочасовую задачу после сбоя

Проблема: длинная цепочка обрывается, а повтор может выполнить внешнее действие второй раз.

Действия инженера:

- Добавить контрольные точки и передачу работы следующей сессии.
- Перед повтором проверять, выполнено ли внешнее действие.
- Неясный случай отправлять на разбор.

Ожидаемый результат: работа продолжается с последней подтверждённой точки. Ни одна запись не переносится дважды.

## Пример 4. Встроить требование Security

Проблема: требование безопасности существует текстом, и агент может выполнить действие до проверки.

Действия инженера:

- Поставить проверку разрешений до выполнения.
- Закрыть обходные способы доступа.
- Задать поведение на случай, когда сама проверка недоступна.

Ожидаемый результат: ограничение действует во всех способах запуска. Причины разрешения и отказа сохраняются. Если проверка недоступна, действие не выполняется.

## Пример 5. Закрыть окно до загрузки профиля

Проблема: между стартом сессии и загрузкой профиля песочницы остаётся возможность выполнить действие.

Действия инженера:

- Изменить запуск так, чтобы до загрузки профиля и политик не выполнялось ничего.
- Добавить эту проверку в конвейер выпуска.

Ожидаемый результат: окно закрыто для всех способов запуска. Версия, где оно появится снова, не проходит выпуск.

## Пример 6. Обновить платформу, не прерывая длительные задачи

Проблема: новая версия среды может оборвать уже идущие многочасовые задачи.

Действия инженера:

- Проверить совместимость сохранённого состояния с новой версией.
- Выпустить её ограниченной долей с автоматическим откатом.
- Заранее предупредить команды.

Ожидаемый результат: версия введена без потери подтверждённых результатов. Проблемы видны до массового распространения.

## Пример 7. Закрыть скрытый канал обмена

Проблема: агенты передают этап через общий файл мимо официальной сети обмена.

Действия инженера:

- Выяснить, почему команде так было удобнее.
- Закрыть доступ к общему хранилищу.
- Добавить в официальный канал поддержку больших сообщений.

Ожидаемый результат: обход технически невозможен, и у команды нет причины его искать.

## Пример 8. Собрать историю нескольких агентов

Проблема: при инциденте не видно, кто передал задачу, какой инструмент был вызван и какое правило это разрешило.

Действия инженера:

- Связать передачу задачи, вызовы, проверки и результаты в одну историю.
- Для каждого действия записать субъекта, права, сработавшее правило и его версию.

Ожидаемый результат: по инциденту восстанавливается последовательность и находится место нарушения.

## Пример 9. Снизить стоимость при росте нагрузки

Проблема: повторные запуски и лишние вызовы увеличивают расход, а сессия может выйти за бюджет.

Действия инженера:

- Найти причины повторных запусков.
- Ввести лимит на сессию и автоматический останов при перерасходе.
- Проверить изменение на ограниченной группе задач.

Ожидаемый результат: перерасход останавливается автоматически. Соотношение цены работы модели к подтверждённому результату снижается.

## Пример 10. Подготовить инфраструктуру к росту

Проблема: текущих узлов, хранилища и сетевых ограничений не хватает на согласованную нагрузку.

Действия инженера:

- Рассчитать мощности, добавить узлы и расширить хранилище состояния.
- Настроить сеть и сетевые политики.
- Перевести конфигурацию в код.

Ожидаемый результат: платформа выдерживает новую нагрузку с запасом. Новые узлы сразу получают те же ограничения. Следующее расширение занимает минуты, а не дни.

## Пример 11. Снять зависимость от одного поставщика модели

Проблема: недоступность одного поставщика останавливает сессии, хотя сами агенты менять не нужно.

Действия инженера:

- Сделать переключение модели настройкой шлюза.
- Проверить, что сохранённое состояние сессий переносится.

Ожидаемый результат: при недоступности поставщика работа продолжается на другой модели без изменения агентов.
